Backend / Tech Lead · 실시간 영상·음성 AI를 서비스로 만든 개발 총괄 — 해외환자 플랫폼 MIMI
💡
해외 환자와 한국 병원을 다국어 비대면 영상 상담으로 잇는 플랫폼 MIMI에서 백엔드·인프라·출시 기술 결정을 총괄했습니다. 핵심은 연구용 데모가 아니라, Agora 영상 통화 위에 STT → 의료 용어 교정 → 실시간 통역·자막을 붙여 품질·지연·비용을 운영 지표로 관리한 실서비스 파이프라인입니다. 그 위에 결제·채팅·검색·LLM 상담·마케팅 어트리뷰션을 NestJS 모노레포와 Terraform AWS로 묶었고, 2026년 9월 일본 · 중국 · 대만 · 미국 · 싱가포르 5개국 앱·웹 정식 출시까지 일정과 안정성을 책임졌습니다.

소수 인원으로 이 규모를 운영한 방식은 AI를 코드 생산에만 쓰지 않고, 서비스 기능으로 제품화한 것입니다. 상담 통역·요약·RAG 에이전트·관상 분석처럼 모델 API를 실제 트래픽 경로에 올리고, 동시에 에이전트 개발(룰·스킬·MCP)과 배포 게이트로 변경 속도를 유지했습니다.

🏗️ 2. 시스템 아키텍처

하나의 NestJS 모노레포에서 Nest 앱 7개와 Strapi가 공통 라이브러리를 공유합니다. 추천 대화 그래프 자체는 이 레포 밖 LangGraph Platform에서 돌고, API는 그 실행을 저장·프록시합니다.

apps/face-reading-apiAI 관상·피부 분석 전용 서비스 (별도 EC2 · ALB)
apps/beauty-trip-plannerK-뷰티 여행 일정 초안. 규칙 엔진은 planner-core, 가이드 문장은 ai-planner. LangGraph 에이전트와는 별개

설계 원칙
  • 엔티티·마이그레이션은 libs/database 한 곳에서 관리하고, 각 앱은 도메인 로직만 소유
  • 에러는 모두 errorCode를 포함한 커스텀 예외로 던지고, 클라이언트는 코드 기반으로 다국어 메시지를 표시
  • MySQL은 쓰기(Primary)와 읽기(Replica)를 분리하되, 쓰기 직후 읽기는 트랜잭션 안이나 master 연결에서만 수행
  • 모든 시간은 UTC로 저장하고, 표시할 때만 클라이언트 시간대로 변환

🎥 3-1. 비대면 영상 상담 · 실시간 통역 (상세)

Agora RTCOpenAI RealtimeGoogle STTGemini fallbackWebSocketRedis

상단 핵심 요약의 상세 버전입니다. 같은 도메인을 상태 머신·세션·품질 게이트 단위로 풀어 썼습니다.

  • 상담 요청 → 병원 수락 → 결제 → 입장 → 종료 → 리뷰로 이어지는 영상 상담 상태 머신을 설계하고, 배치로 상태를 전이시키는 흐름을 구현
  • Agora 토큰 발급과 통화 세션 관리, 수신 전화 푸시(APNs VoIP / FCM) 연동
  • 의사와 해외 환자 사이 실시간 음성 통역: OpenAI Realtime API를 WebSocket으로 중계하고, 발화가 끝나면 최종 교정 단계를 한 번 더 거치는 2단계 파이프라인 구성
  • STT TERM-only 결정론 교정, 조건부 LLM post-edit, 번역 glossary/style rewrite, Google STT·Gemini fallback으로 품질을 지키면서 지연·비용을 제한
  • 상담 종료 후 STT와 LLM으로 상담 요약본을 자동 생성하고, STT 품질 QA·배치 회귀 도구 제작
  • 상담권, 상담 가격 정책, 병원별 상담 가능 스케줄 관리

💬 3-2. 실시간 채팅 (미미톡)

Socket.ioRedis AdapterMongoDBALB Sticky
  • 병원과 환자가 상담 이후에도 계속 대화하는 영속 1:1 채팅을 설계 (메시지는 MongoDB, 상태·권한은 MySQL)
  • ECS 다중 태스크 환경에서 Socket.io Redis Adapter와 ALB 스티키 세션으로 수평 확장
  • 일정 제안, 예약금 결제, 방문 확정, 취소 요청 같은 시스템 카드 템플릿으로 대화 안에서 예약 전환까지 이어지도록 구성
  • 안 읽은 메시지를 모아 알림톡으로 리마인드하는 스케줄러 구현

💳 3-3. 결제 · 예약금 · 정산 대사

TossPaymentsMySQL 트랜잭션멱등성
  • 토스페이먼츠 결제 승인·취소·환불과 주문 원장(ledger) 설계
  • 대사(reconciliation) 스케줄러로 PG사 기록과 내부 원장의 불일치를 탐지하고, 미결제 주문은 만료 스케줄러로 정리
  • 영상 상담 결제와 대면 상담 예약금을 한 결제 체계로 통합하고, 상담 취소 시 환불과 상담권 복구가 한 흐름으로 처리되도록 구성
  • 영수증 검증, 리워드, 추천인 이벤트 등 보상 도메인
  • 운영 이벤트: 체험단 신청 · 선정과 룰렛. 비회원이 기기 ID로 룰렛을 돌린 기록을 로그인 뒤 회원 신청에 연결하고, 비회원 신청자에게는 쿠폰 코드를 메일로 발송. 메일의 앱 링크는 앱이 없으면 스토어로 이동하며, 1등 응모권은 쿠폰함 이력에 기록

🔎 3-4. 통합 검색 엔진

OpenSearch + noriQdrantCohere Rerank
  • 병원·시술·의사·기획전을 한 번에 찾는 다국어 통합 검색을 OpenSearch로 구축하고, 한국어 형태소 분석(nori) 적용
  • 워터마크 기반 동기화: last_modified_at을 30초마다 폴링해 바뀐 섹션만 다시 색인. 벌크 색인이 한 건이라도 실패하면 워터마크를 전진시키지 않도록 설계
  • 매핑이 바뀌면 새 버전 인덱스 생성 → 전량 재색인 → 검증 → alias 원자 전환 순서로 무중단 재색인
  • 시술 개념(컨셉) 사전과 alias, 쿼리 정규화, 이름 prefix 엔티티 인식, 섹션 필터 탭 구현
  • Qdrant 벡터 검색을 함께 사용하고, NDCG 기반 랭킹 베이스라인으로 검색 품질을 평가

🤖 4. AI-Native 개발 워크플로우

🧠
핵심 관점 — AI가 코드를 빠르게 쓰는 것은 이제 기본입니다. 차이는 AI에게 어떤 맥락을 주고(Context Engineering), AI가 만든 결과를 무엇으로 검증하느냐(Guardrails as Code)에서 납니다. 저희 팀은 “프롬프트를 잘 쓰는 사람”에 기대지 않고, 좋은 프롬프트가 되는 맥락 자체를 리포지토리에 코드처럼 쌓아 둡니다. 누가 에이전트를 돌려도 같은 품질이 나오게 하는 것이 목표입니다.

4-1. 에이전트에게 주는 맥락: 3개의 층

📏 Rules — 항상 지켜야 할 규칙 (17개)

  • 에러 코드 필수, Swagger 응답 타입, 엔티티 위치, UTC 저장 같은 프로젝트 헌법
  • Replica 지연, 분산 스케줄러, 검색 워터마크, TypeORM 성능, Mongo 스캔량, 영상 상담 컨텍스트처럼 실제 사고에서 나온 규칙
  • 로컬 migration:run 금지, Terraform은 지정 AWS 프로파일만 사용 같은 위험 작업 차단

🧰 Skills — 도메인 운영 지식 (11개)

  • 알림톡, 푸시 알림센터, 딥링크·유입 추적, 통합 검색 재색인, 병원 채팅, 전후사진 크롤, 헤어샵, Grafana, Swagger orval 제외
  • “새 알림톡 시나리오 추가”처럼 여러 레포와 외부 콘솔에 걸친 절차를 에이전트가 순서대로 수행
  • 운영 DB 접속은 bastion·SSM 절차 스킬로만 허용

🔌 MCP — 실제 시스템에 연결

  • MySQL MCP로 dev DB 스키마와 데이터를 직접 확인하고 코드를 작성 (추측으로 쿼리를 쓰지 않음)
  • Figma MCP로 디자인을 읽어 API 계약을 맞추고, 라이브러리 문서 MCP로 최신 API 확인
  • DB에 DDL을 실행하면 엔티티와 마이그레이션을 반드시 함께 수정하도록 룰로 강제

📝 Specs — 구현 전 합의 (123개)

  • 에이전트가 먼저 기획 의도, 예외 상황, 트레이드오프를 인터뷰하고, 합의된 내용을 스펙 파일로 작성
  • 스펙이 에이전트의 작업 지시서이자 리뷰 기준, 이후 유지보수 문서가 됨
  • 아키텍처 문서 35편 이상, 운영 런북 함께 관리

4-2. 기능 하나가 반영되는 흐름

1
사람 + AI요구사항 인터뷰 → 스펙 작성에이전트가 기술 구현, UX, 우려 사항, 트레이드오프를 질문하고 docs/specs/에 스펙으로 정리합니다.
2
AI맥락 로딩 → 구현룰은 자동으로 적용되고, 관련 스킬을 읽고, MCP로 실제 스키마를 확인한 뒤 엔티티·마이그레이션·서비스·DTO·Swagger를 한 번에 작성합니다.
3
AI스스로 검증핵심 로직마다 실패하면 바로 드러나는 테스트를 남기고, 빌드·린트·관련 Jest를 실행해 통과시킨 뒤 작업을 끝냅니다. 룰에 “검증 없는 코드는 미완성”이라고 명시되어 있습니다.
4
AI 리뷰 + 사람리뷰리뷰 에이전트로 버그와 보안을 1차로 보고, 사람은 PR 템플릿의 PROJECT_RULES 체크리스트를 기준으로 의도와 설계를 봅니다. 한 줄씩 읽는 대신 “이 변경이 스펙과 룰을 지키는가”를 봅니다.
5
CI자동 게이트 통과 후 배포아래 4-4의 4단계 게이트를 통과해야 운영에 반영됩니다.
6
사람 + AI사고 → 룰로 환원장애가 나면 원인을 분석해 룰이나 스킬 한 줄로 되돌려 놓습니다. 같은 실수는 다음 에이전트부터 반복되지 않습니다.

4-3. 사고가 규칙이 되는 피드백 루프

룰은 처음부터 설계한 것이 아니라, 운영하면서 생긴 사고를 하나씩 코드화한 결과입니다.

사고 / 문제에이전트 룰로 만든 것
상담 취소 커밋 직후 Replica에서 읽어 환불이 누락됨typeorm-replica-read-after-write — 커밋 후 판단에 쓰는 조회는 master로 읽고, Replica로 되돌리면 실패하는 테스트를 남김
다중 태스크에서 알림이 중복 발송됨scheduler-distributed-execution — 스캔 lease와 아이템 claim 없이는 외부 발송 금지
상세 API가 조인 폭증과 직렬 await로 느려짐typeorm-relations-performance — 1:N 관계 동시 로딩 금지, 독립 조회는 Promise.all
로컬 서버가 Docker DB를 바라봐 잘못된 데이터로 개발local-api-uses-rds — 잘못된 DB 설정을 발견하면 즉시 고치고, 시작 스크립트에서 차단
AI가 불필요한 추상화와 코드를 과하게 생성lazy-senior-dev — 표준 라이브러리 → 기존 의존성 → 최소 코드 순서로 판단. 단순화한 부분은 한계와 개선 방향을 주석으로 남김

4-4. AI 시대의 안정적인 배포: “AI가 만든 코드를 AI도 사람도 믿지 않는 구조”

코드 생산 속도가 몇 배로 빨라지면 사람이 모든 줄을 리뷰하는 방식은 버틸 수 없습니다. 그래서 신뢰의 근거를 사람의 눈에서 자동화된 증거로 옮겼습니다. 머지와 배포는 각 게이트가 초록색일 때만 가능합니다.

① PR: 전체 Jest + critical path + PMC 시뮬레이션→ ② dev EC2 Blue-Green + 헬스체크→ ③ main 필수 체크: PMC 시뮬레이션→ ④ prod: env 검증 → 마이그레이션 → CodeDeploy → 헬스체크
① PR 단계PR에서 전체 Jest와 critical path를 돌립니다. 환자 앱·병원 어드민이 실제로 보내는 메신저 상담 요청은 컨트롤러와 ValidationPipe로 흘리는 PMC 시뮬레이션이 라우팅·DTO 회귀를 막습니다. DB와 배포가 없어 1~2분이면 끝납니다.
② dev 배포dev EC2에 Blue-Green으로 배포하고 헬스체크가 통과해야 트래픽을 전환합니다. 에이전트가 만든 변경도 먼저 실제 인프라(Dev RDS, Redis, 외부 API) 위에서 동작해 봐야 합니다. 배포 직후 상담 전 과정을 밟던 PVC smoke는 2026-10부터 워크플로에서 뺐습니다.
③ main 머지dev·main PR의 필수 status check는 pmc simulation guard입니다. 건너뛰면 pending으로 남아 머지가 멈추므로 path 필터를 두지 않습니다. 예전처럼 dev smoke 성공을 최대 20분 기다리던 main PR guard는 제거했습니다.
④ prod 배포GitHub OIDC로 키 없이 AWS에 접근합니다. Secrets Manager의 env에 필수 키가 모두 있는지 먼저 검증하고, Fargate 일회성 태스크로 마이그레이션을 실행한 뒤, CodeDeploy로 ECS에 배포하고 헬스체크로 확인합니다. 검색 색인·Qdrant·페르소나 워커는 별도 잡입니다. 마이그레이션은 CI에서만 실행하고 로컬·에이전트 실행은 룰로 막습니다.

🛠️ 5. 문제 해결 사례

① Replica 지연 때문에 환불이 조용히 누락된 사고

문제 상담 취소를 커밋한 직후, 환불 서비스가 같은 행을 Replica에서 읽었습니다. 복제가 몇 ms 늦으면 아직 취소 전 상태로 보여 환불할 수 없는 건으로 판단했고, 환불과 상담권 복구가 통째로 건너뛰어졌습니다.

해결 커밋 후 판단에 쓰는 조회는 모두 master 연결로 옮겼습니다. 재사용하는 조회 함수는 선택적으로 EntityManager를 받아, 쓰기 경로에서만 master를 쓰도록 했습니다. 일반 목록·상세 조회는 Replica에 남겨 master 부하가 늘지 않게 했습니다.

재발 방지 Replica 조회로 되돌리면 실패하는 테스트를 남기고, 팀 코드 리뷰 규칙으로 문서화했습니다.

② 다중 태스크 환경에서 알림이 중복 발송되는 문제

문제 ECS 태스크가 2개 이상 뜨면 메모리 플래그(isProcessing)만으로는 스케줄러 중복 실행을 막을 수 없어, 알림톡이 두 번 나가는 경우가 있었습니다.

해결 MySQL 실행 테이블에 스캔 lease와 아이템 claim을 두 단계로 두고, 조건부 업데이트로 실행권을 얻은 태스크만 외부로 발송하도록 바꿨습니다. dedupe 키에는 타임스탬프 같은 매번 달라지는 값을 넣지 않도록 규칙을 만들었습니다.

③ 상세 API 응답 지연 (조인 폭증과 직렬 await)

문제 병원 상세 조회에서 번역·이미지·의사처럼 1:N 관계 여러 개를 relations로 한 번에 불러오면서 조인 결과가 폭증했고, 서로 관계없는 조회를 순서대로 await해 지연이 누적됐습니다.

해결 1:1 관계만 먼저 불러오고, 1:N 관계는 별도 쿼리로 나눠 Promise.all로 병렬 실행했습니다. 이미 집계한 값은 다시 COUNT하지 않고 메모리에서 합산했습니다. 구간 타이밍과 쿼리 캡처로 원인을 확인한 뒤 최적화했습니다.

④ 검색 인덱스와 DB의 불일치

문제 색인 중 일부가 실패해도 워터마크가 전진하면, 해당 변경분이 검색에 영원히 반영되지 않을 수 있었습니다.

해결 벌크 색인이 한 건이라도 실패하면 오래된 문서 정리와 워터마크 전진을 모두 멈추도록 했습니다. 물리 삭제나 백필 이후에는 강제 동기화 명령을 실행하도록 운영 런북을 만들었습니다.

🧭 6. 일하는 방식

“가장 좋은 코드는 쓰지 않은 코드다.” 필요한 만큼만 만들고, 대신 데이터 정합성·보안·장애 대응에는 타협하지 않습니다.
  • 문서 기반 개발: 기능마다 스펙 문서를 먼저 쓰고 구현합니다. 아키텍처 문서 35편 이상을 작성했고, 사고가 나면 원인과 재발 방지 규칙을 팀 룰로 남깁니다.
  • 운영 가능한 설계: 모든 스케줄러와 결제 흐름은 운영 중 SQL로 추적할 수 있게 만들고, 머지 전에는 상담 요청 시뮬레이션으로 라우팅·DTO 회귀를 막습니다.
  • 풀스택 협업: Swagger를 orval과 연동해 환자 앱(React Native)과 병원 어드민의 API 클라이언트를 자동 생성하고, 프론트엔드와 계약을 맞춥니다.
