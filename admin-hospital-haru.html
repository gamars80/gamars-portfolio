🧩 3. 두 프로젝트 공통 설계

📜 API 계약 자동화

  • NestJS Swagger 스펙에서 orval로 React Query 훅과 타입을 자동 생성
  • 모든 응답에 타입을 지정하도록 강제해 프론트엔드가 추측으로 타입을 쓰지 않게 함
  • 내부 운영 전용 API는 병원 어드민 클라이언트에 생성되지 않도록 Swagger에서 분리

🔐 권한 분리

  • 병원 계정은 자기 병원 리소스만 접근 (리소스 소유권 가드)
  • Haru Agent는 SUPER_ADMIN과 내부 직원(ADMIN) 계정만 로그인. CS 메뉴는 내부 운영 병원 소속 운영자만 접근
  • 번역 검수자 전용 홈과 언어별 검수 화면 분리

🌏 다국어 운영

  • 병원은 한국어로 입력하고, 환자에게는 5개 언어로 노출
  • 원문이 바뀌면 자동 번역하고, 수동 번역은 출처와 최신 여부를 표시
  • 에러는 에러 코드 기반으로 클라이언트에서 메시지 처리

🛡️ 운영 사고 방지

  • 대량 발송 · 노출 전환처럼 되돌리기 어려운 작업은 저장 · 검증 후에만 실행
  • 삭제는 모두 소프트 삭제
  • 이미지는 S3 presigned URL로 업로드하고 형식 · 용량 제한

🤖 4. AI 기반 개발 방식

⚡
Haru Agent의 운영 기능은 대부분 하나의 AI 에이전트 작업 흐름으로 백엔드와 프론트엔드를 함께 만들었습니다. 스펙을 먼저 쓰고, resta_api에서 엔티티 · 마이그레이션 · API · Swagger를 만든 뒤, orval로 타입을 생성하고 바로 Haru Agent 화면을 붙입니다. 기능 하나가 보통 PR 1~3개로 dev에 반영됩니다.
  • 프로젝트별 룰: 병원 어드민은 프론트엔드 아키텍처(container / views 분리), 디자인 토큰 매핑, UX 문구 톤 룰을, Haru Agent는 프론트 공통 룰을 에이전트에게 항상 적용
  • worktree 병렬 작업: 기능마다 별도 git worktree를 만들어 여러 에이전트 작업을 동시에 진행하고, 기능 단위로 작은 PR을 올림
  • 계약 우선: 백엔드 Swagger가 먼저 확정되고 프론트는 생성된 타입에 맞춰 작성하므로, 에이전트가 API를 추측해 잘못 연결하는 일이 줄어듦
  • 운영 피드백 루프: 운영팀이 쓰다가 불편한 점(예: 캠페인 생성 후 목록 복귀, 빈 문자열 필터 버그)을 받으면 작은 수정 PR로 바로 반영

※ 기능 범위는 각 리포지토리의 README · 화면 구성을 기준으로 정리했습니다 (2026.11). “직접 구현”은 본인 커밋 기준이며, 그 밖의 화면은 팀원이 구현하고 본인은 API를 담당했습니다.
