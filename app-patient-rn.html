🧱 2. 앱 구조

앱 코드에서 확인한 구조입니다. 서버를 설계할 때 이 구조를 전제로 계약을 맞췄습니다.

부팅업데이트 확인 화면에서 강제 업데이트 판정 → OTA 번들 확인 → A/B 실험 배정을 기다린 뒤 진입. 앱을 계속 켜 두는 사용자를 위해 포그라운드 복귀 때 OTA를 다시 확인하고 다음 실행에 적용
서버 통신Swagger에서 orval이 만든 TanStack Query 훅과 타입만 사용. 401을 받으면 refresh 요청을 한 번만 보내고(single-flight) 토큰을 교체
상태서버 상태는 TanStack Query, 클라이언트 상태는 Zustand, 영속 저장은 MMKV
영상 통화Agora RTC. 실시간 통역 자막과 전사 동기화는 Socket.io
전화 수신iOS는 PushKit(VoIP) + CallKit, Android는 FCM 데이터 메시지 + 전체 화면 알림. Android 14 이상의 전체 화면 인텐트 권한은 Kotlin 네이티브 모듈로 처리
AI 채팅LangGraph 실행 스트림을 SSE로 수신. RN의 fetch 스트리밍이 불안정해 XHR 진행 이벤트로 SSE를 파싱
알림 · 딥링크푸시를 누르면 알림 종류와 navigation 값으로 화면 이동. Universal Links · App Links와 설치 후 첫 실행 딥링크 처리
분석 · 실험자체 이벤트 수집, Firebase(GA4), Airbridge(MMP), Clarity. Firebase Remote Config로 A/B 실험 배정
다국어i18next 5개 로케일. 서버 에러는 에러 코드로 받아 앱에서 언어별 문구로 표시

🔌 3. 앱 기능과 서버 구현

앱 화면 뒤에서 제가 설계하고 구현한 서버입니다. 상세는 백엔드 이력서의 도메인별 경험에 있습니다.

앱 기능Backend서버에서 만든 것
푸시 · 알림함문구 렌더 → DB 저장 → FCM 발송 순서의 save-first 구조. 푸시가 실패하거나 수신 거부여도 알림함에는 남음. 앱 화면 이동은 화면 이름이 아니라 type + payloadVersion + navigation 계약으로 전달해 앱 화면 구조가 바뀌어도 서버를 고치지 않음. dedupe 키로 중복 방지, 180일 보관. FCM 발송은 API와 분리한 전용 워커(별도 Fargate)
상담 신청 · 미미톡메신저 상담 신청 자격 판정과 상태 전이, 병원–환자 1:1 채팅(메시지는 MongoDB, 상태 · 권한은 MySQL), 일정 제안 · 예약금 · 방문 확정 시스템 카드, 안 읽은 메시지 알림톡 리마인드
영상 상담요청 → 수락 → 결제 → 입장 → 종료 → 리뷰 상태 머신, Agora 토큰과 통화 세션, 실시간 음성 통역 중계(OpenAI Realtime), 상담 종료 후 요약 생성
결제 · 쿠폰앱은 토스 결제창을 WebView로 띄워 해외 카드로 결제. 서버는 승인 · 취소 · 환불, 주문 원장, PG 대사 스케줄러, 상담권 · 쿠폰 발급과 회수
통합 검색OpenSearch 기반 병원 · 시술 · 의사 · 기획전 다국어 검색, 워터마크 동기화, 무중단 재색인
AI 상담 에이전트에이전트는 LangGraph Platform에서 실행하고 앱이 실행 스트림을 직접 수신. 서버는 스레드 생성, 대화 메시지 동기화(MongoDB), 병원 · 시술 · 리뷰 메타데이터 보강을 담당

룰렛 · 이벤트이벤트 신청 · 선정, 응모권 · 쿠폰함 이력, 비회원이 기기 ID로 룰렛을 돌린 기록을 가입 후 회원 기록에 연결, 쿠폰 메일의 앱 링크는 앱이 없으면 스토어로 이동

🚀 4. OTA 배포 인프라

Infra스토어 심사 없이 JS 번들을 내보내는 코드 푸시 경로

hot-updater · AWS S3 + CloudFront + Lambda@Edge · Terraform · dev / production 채널
  • OTA 스택 전체를 Terraform으로 구성: 번들 저장 S3, CloudFront(OAC), 업데이트 확인을 처리하는 Lambda@Edge, 번들 서명 키(SSM), 액세스 로그 버킷(90일 보관)
  • RN 개발자가 명령 한 줄로 dev · production 채널에 배포할 수 있도록 배포 가이드를 작성하고, Terraform output을 앱 설정의 정본으로 지정
  • CloudFront 액세스 로그로 업데이트 확인 요청 수 대비 번들 다운로드 수를 비교해, 앱이 보내는 지표를 서버 쪽에서 교차 검증
  • OTA 배포 현황 대시보드(Grafana): 번들을 내보낸 뒤 실제 단말에 퍼지는지, 업데이트 확인 실패율과 최신 번들 도달률을 배포 직후에 확인

📜 5. 앱–서버 계약과 배포 게이트

API 계약 자동화

  • NestJS Swagger 스펙에서 orval이 앱의 React Query 훅과 타입을 생성
  • 모든 응답에 타입 지정을 강제해 앱이 응답 모양을 추측하지 않게 함
  • 내부 운영 전용 API는 앱 클라이언트에 생성되지 않도록 Swagger에서 분리

앱 요청으로 막는 서버 회귀

  • 앱과 병원 어드민이 실제로 보내는 상담 요청을 컨트롤러와 ValidationPipe에 흘리는 요청 시뮬레이션 테스트 작성
  • dev · main 머지의 필수 체크로 지정. DB와 배포 없이 1~2분에 끝나 라우팅 · DTO 변경이 앱을 깨기 전에 차단

다국어 · 시간대

  • 서버는 에러 코드만 내려주고 문구는 앱이 5개 언어로 표시
  • 푸시 · 알림 문구는 서버 템플릿에서 환자 언어로 렌더
  • 모든 시간은 UTC로 저장하고 앱이 환자 시간대로 변환

앱과 서버에 걸친 작업의 절차화

  • 새 푸시 종류 추가처럼 서버 · 앱 · 템플릿이 함께 바뀌는 작업을 에이전트 스킬 문서로 정리
  • 기능마다 스펙 문서를 먼저 쓰고, 서버 계약을 확정한 뒤 앱이 생성된 타입에 맞춰 구현

🛠️ 6. 문제 해결 사례

미국 신규 설치 사용자가 OTA 업데이트를 받지 못한 문제

2026.08 · CloudFront Function · 업데이트 확인 3.8초 → 0.04~0.14초
문제새 번들을 내보내도 미국 사용자는 업데이트를 건너뛰었습니다. 앱은 업데이트 확인이 타임아웃되면 “업데이트 없음”으로 처리하고 이를 “최신 상태”로 집계해, 실패가 지표에 드러나지 않았습니다.
원인업데이트 확인 URL의 마지막 값(cohort)이 기기마다 다른 1~1000 숫자였습니다. 같은 응답을 받을 단말이 캐시 키를 1000개로 나눠 가져, 요청이 적은 미국 엣지에서는 거의 모든 요청이 서울 S3까지 왕복했습니다. 액세스 로그 16시간 기준 미국 캐시 적중 0/34, 평균 4.03초였고, 캐시 TTL을 1년으로 올려도 풀리지 않았습니다.
제약앱에서 cohort를 고정하는 수정은 OTA 번들 안에 들어갑니다. 신규 설치는 스토어 번들로 첫 확인을 하므로, 앱 수정만으로는 다음 스토어 릴리스 전까지 신규 사용자를 구제할 수 없었습니다.
해결CloudFront Function(viewer-request)으로 엣지에서 cohort 값을 하나로 치환해 캐시 키를 합쳤습니다. 캐시 조회 전에 실행되고 지연이 1ms 미만이라 Lambda@Edge 대신 골랐습니다. 운영 중인 번들 410개가 모두 전체 배포 상태라 응답이 바뀌지 않는다는 것을 먼저 확인했고, QA 타겟팅용 값과 구버전 SDK 경로는 치환에서 제외했습니다.
결과한 번도 요청된 적 없는 cohort 6개가 모두 캐시 적중 0.04~0.14초로 응답했습니다(적용 전 3.81초). 스토어 릴리스를 기다리지 않고 신규 설치 사용자까지 적용됐습니다.
남긴 것치환 규칙의 자체 검증 테스트, Terraform 변수 하나로 되돌리는 롤백 절차, “단계적 배포를 쓰려면 이 함수를 먼저 뗀다”는 전제를 문서로 남겼습니다. 같은 종류의 조용한 실패를 배포 직후에 보도록 OTA 배포 현황 대시보드를 만들었습니다.

※ 앱 구조와 화면 범위는 resta-patient develop 기준입니다 (2026.11). 앱 화면과 네이티브 코드는 RN 개발자 2명이 구현했고, 본인은 개발 총괄로서 API · 실시간 서버 · 푸시 · 결제(resta_api)와 OTA 인프라를 담당했습니다. 서버 항목은 resta_api 본인 커밋 기준입니다.
